# ADR-0108: 语音 v3：后台串行预置、抗 CPU 争用基准门控与前端单一进度指示

- **状态**: Accepted
- **日期**: 2026-10-02
- **决策者**: 用户（需求）/ Opus（设计）/ Gemini（实现）
- **相关模块**: M13 Gateway / `cmd/polaris/` / `internal/config/` / `internal/llm/audiorun/` / `internal/gateway/server/chat/` / `web/src/`
- **取代**: ADR-0107 决策 3（按需下载）与反例守护第一条（拒绝启动期自动下载语音资产）。ADR-0107 的模型选型、最低硬件门控、懒加载/空闲卸载、错误契约依然有效。

## 上下文

ADR-0107 实施后，用户在日常使用中暴露 5 个相互关联的体验与稳定性缺陷（R1–R5）：
1. **R1 启动零下载导致初次使用长等待**：ADR-0107 决策 3 规定启动不下载任何模型，用户首次点击麦克风时必须原地等待数百兆下载；而朗读因降级系统语音显得"自动就绪"，体验割裂。
2. **R2 进度 toast 刷屏**：前端轮询高频触发无 key 机制的 toast，多条提示重叠闪烁，视觉干扰严重。
3. **R3 TTS 首次基准被 CPU 争用污染**：同一台机器在空闲时 Kokoro fp32 跑出 RTF 0.42，但在安装后立即基准时因与后台任务（向量回填、runner 预热、另一路解压）抢占 CPU，跑出 RTF 1.10，被误判为 `too_slow` 导致模型白下载并永久降级。
4. **R4 STT/TTS 两路并行安装资源踩踏**：用户操作可能并发触发两路下载与 bz2 解压，带宽分摊且 CPU 抢占严重，进一步加剧 R3。
5. **R5 原生对话框不可靠**：前端依赖 `window.confirm`，在 Tauri WebView 及各浏览器环境下弹窗表现不一，且阻断操作。

## 决策

1. **D1 安装后自动后台预置**：
   - 增加配置 `inference.audio.auto_install = true`（默认开启）。
   - 守护进程启动后延迟 45 秒（避开启动期向量回填与 runner 预热高峰），由单一预置器（Provisioner）**串行**执行：先 STT（核心能力、体积较小），再 TTS。
   - 预置器仅下载和校验资产，不常驻引擎（保留懒加载与空闲卸载语义）。TTS 首次基准完成后立即卸载。
   - 失败采用指数退避：5m → 30m → 2h，单进程内最多自动重试 3 次；耗尽后保持 `failed` 并提供重试按钮。
   - 用户手动点击与后台预置共享原子锁，避免重复下载。
2. **D2 TTS 首次基准抗 CPU 争用门控**：
   - 基准前通过采样系统 CPU 占用率等待空闲：连续 3 次 < 50% 视为空闲（预置路径最多等 10 分钟；用户触发路径立即测试）。
   - 记录基准前后 CPU 占用，任一 ≥ 50% 判定为 `Contended=true`。
   - 表驱动判定：
     - 若 RTF ≤ 0.8：判 `Supported=true`，持久化并复用。
     - 若 RTF > 0.8 但争用（`Contended=true`）：判暂时不可用，**不落定论**，置 `RetryOnStart=true`，状态发布 `ready`，退回系统语音，等待下一个空闲窗口自动重测。
     - 若 RTF > 0.8 且无争用：首次给予一次重测机会；仅在重测仍超标时才定论 `Supported=false, RetryOnStart=false`。
3. **D3 朗读后端策略**：
   - Kokoro 就绪且基准通过走服务端；下载中、不支持、基准未通过或配置指定时，平滑降级至前端浏览器本地系统中文语音；无可用语音时明确提示不可用。严禁引入云端外送语音。
4. **D4 前端单一进度指示与零 Toast 体验**：
   - 新建 `audio` store 统管全局语音状态，轮询轻量接口 `GET /v1/audio/status`。
   - 进度集中于底部状态栏单一 chip，下载过程屏幕零 toast 刷新。
   - toast store 支持 `key` 覆盖去重。麦克风/朗读按钮在下载中呈现等待态，点击仅刷新单条状态 toast。
   - 废除 `window.confirm`；仅当 `auto_install=false` 且首次触发时，弹出页内 DaisyUI modal 询问。
5. **D5 范围边界**：
   - 不改动模型、资产清单及 sha256；不改动懒加载与空闲卸载生命周期；不改动 FFI ABI；不依赖 Web Speech API。

## 后果

- **正向**:
  - 核心语音能力开箱即用，后台静默准备，无需初次使用繁琐等待与确认弹窗。
  - 彻底解决下载进度 toast 刷屏问题。
  - 消除瞬时 CPU 争用导致的 TTS 误判，保护可用机器不被错误禁用。
  - 串行化安装解压彻底消除两路并发资源抢占。
- **负向**:
  - 本轮不做跨平台磁盘空间预检，依赖已有下载器的物理写入失败防护。
  - 启动后 45s 会有短暂后台网络和解压 CPU 开销（通过串行和低优先级延迟已最大程度平抑）。
- **反例守护**:
  - 拒绝并行安装 STT 与 TTS 资产。
  - 拒绝在 CPU 争用（`Contended=true`）下得出 too_slow 定论。
  - 拒绝使用 toast 定时刷新展示下载进度。
  - 拒绝在桌面端与 Web 客户端中使用阻塞式 `window.confirm`。

## 被驳回的方案

| 方案 | 驳回理由 |
|------|---------|
| 并行并发安装 STT 与 TTS | 网络带宽与 CPU 解压互相抢占，极易污染 TTS 基准，导致低配机器卡顿崩溃 |
| 启动期同步立即下载 | 拖慢守护进程启动就绪时间，严重踩踏启动期向量回填与模型预热高峰 |
| 维持 toast 进度轮询刷新 | 无 key 替换导致同屏多条叠加刷屏，对用户造成严重认知干扰 |
| 单次 RTF 超标即定论 too_slow | 忽视瞬时负载抢占（如 runner 预热），导致支持的机器被永久误杀降级 |
